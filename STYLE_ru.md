# Стиль кодирования на C — Mirva

> В разработке (активно изменяется)

## Принцип

Всё, что не запрещено, — разрешено.

## Архитектура и модули

- Масштабировать архитектуру модульно.
- Упор на композицию и интерфейсы, а не на иерархические структуры.
- Избегать иерархии: глубоко вложенных структур и длинных цепочек зависимостей между модулями.
- Всё разграничено по каталогам.
- Модуль — это каталог; под каждый модуль выделяется собственный вложенный каталог. Модуль инкапсулирует определённый аспект функциональности.
- Один файл — одна сущность.
- Потребитель видит модуль через заголовок (см. «Заголовки»).

### Инкапсуляция

- Через непрозрачные (opaque) типы.
- Публичный и приватный заголовки; приватный получает суффикс `_internal` в имени файла.

## Именование

- Типы — PascalCase.
- Процедуры — snake_case.
- Поля структур — snake_case.
- Элементы `enum` — PascalCase.
- Константы — `SCREAMING_SNAKE_CASE`.
- Макросы — `SCREAMING_SNAKE_CASE`; функциональные макросы, которые должны выглядеть единообразно с функциями, — snake_case.
- Избегать сокращений и аббревиатур в названиях.
- Исключение — общепринятые аббревиатуры, например `AABB` (bounding box).
- Сокращения допустимы для локальных участков кода, строго контролируемо и только при реальной необходимости: когда это улучшает читабельность и упрощает написание вычислений.
- Операции жизненного цикла — суффиксом к имени типа (см. «Жизненный цикл объектов»).

### Префиксы

**По структуре или по файлу.** Префикс должен соответствовать модулю — единице API, которую видит потребитель, то есть заголовочному файлу. В большинстве случаев имя модуля совпадает с именем основной экспортируемой структуры, и различие между «по структуре» и «по файлу» исчезает: `widget.h` экспортирует `struct widget` и функции `widget_*`.

Различие становится значимым только тогда, когда модуль и тип не совпадают. Правила для этих случаев:

#### Модуль экспортирует несколько типов

Префикс остаётся на уровне модуля, имя типа — второй сегмент:

```c
net_conn_create(), net_conn_destroy()
net_packet_alloc(), net_packet_free()
```

Альтернатива — сделать имя типа составным (`struct net_conn`), тогда префикс функции естественно совпадает с типом. Оба варианта корректны; важно не смешивать их в одном модуле.

#### Тип охватывает несколько файлов

Префикс привязан к типу, файлы — лишь разбиение реализации:

```text
widget.c        → widget_create, widget_init
widget_render.c → widget_render, widget_draw
widget_event.c  → widget_on_event, widget_dispatch
```

Потребитель воспринимает это как один API `widget_*`, независимо от числа `.c`-файлов.

#### Утилитарный модуль без доминирующего типа

Префикс модуля, без привязки к структуре:

```text
str_dup, str_split, str_join
hash_compute, hash_compare
```

#### Ограничения

Не использовать в качестве префикса общие имена (`list_`, `node_`, `item_`, `context_`) без квалификации модулем. В плоском пространстве имён C это прямой путь к коллизиям при компоновке. Либо `sched_list_*`, либо уникальное имя типа `sched_list`.

## Форматирование

- Отступ — 4 пробела.
- Открывающая `{` никогда не переносится на новую строку, в том числе в функциях.

### Объявления

- `*` в объявлении указателя прижат к имени переменной: `int *ptr;`.
- Мультидекларации переменных через запятую запрещены.

## Структура кода

### Вложенность

- Максимум 3 уровня вложенности.
- Уровень 1 — тело функции. Каждый вложенный блок (`if` / `for` / `while` / `switch`) добавляет +1.
- Следствие: внутри функции допускается не более двух вложенных блоков.
- Если лимит превышен — разрешать через инварианты или выносом логики в отдельные процедуры.
- Инварианты — способ написать код так, чтобы вложенность была меньше.

### goto

- `goto` строго запрещён, если не преследуется цель оптимизации.

## Комментарии

- Комментариев нет.
- Документация публичного API в публичных заголовках допускается.
- Исключения — только там, где без комментария код вводит в заблуждение:
  - непредвиденная работа логики: неочевидное поведение, воркэраунды (баг компилятора, особенность платформы или железа);
  - места, которые при простом чтении кажутся непонятными, странными или экстраординарными;
  - пометки о необходимости изменить код, в том числе о будущих изменениях. Такие пометки живут в коде, пока в них есть потребность; рекомендуемый формат — `TODO:` / `FIXME:` / `XXX:`, но он не обязателен.

## Жизненный цикл объектов

### Определение

**`init` / `deinit`** — функции инициализации и деинициализации объекта, хранилище которого предоставлено вызывающим кодом. Хранилище под саму структуру не выделяется и не освобождается. Внутренние ресурсы объекта (буферы, дескрипторы, блокировки, регистрации) приобретаются в `init` и освобождаются в `deinit`.

**`create` / `destroy`** — функции, владеющие хранилищем структуры. `create` выделяет хранилище, инициализирует объект и возвращает указатель на него. `destroy` деинициализирует объект и освобождает хранилище. Реализуются как `malloc` + `init` и `deinit` + `free`.

### Имена функций жизненного цикла

Операция (`create`, `destroy`, `init`, `deinit`) ставится **суффиксом** к имени типа: `widget_create`, `widget_destroy`, `widget_init`, `widget_deinit`. Это обеспечивает:

- группировку всех функций типа под общим префиксом (`widget_*`) в плоском пространстве имён C;
- предсказуемость поиска и автодополнения;
- совместимость с практикой крупных проектов (Git: `commit_list_insert`; wlroots: `wlr_backend_create`).

Суффиксы `alloc` / `free` также допускаются как функции управления жизненным циклом памяти, но только если они не выполняют ничего, кроме выделения и освобождения памяти. Скорее это служебные функции для внутреннего использования, а не для внешнего API.

### Правила выбора

1. Opaque-тип → `create`/`destroy` необходимы: вызывающий код не располагает размером структуры и не может предоставить хранилище.
2. Не-opaque тип → достаточно `init`/`deinit`. `create`/`destroy` опциональны.
3. Оба сценария использования → обе пары; `create`/`destroy` определяются через `init`/`deinit` без дублирования логики.
4. Отсутствие внутренних ресурсов, требующих освобождения → `deinit` не определяется.
5. Отсутствие инвариантов инициализации → `init` не определяется; применяется агрегатная инициализация.
6. Выделение памяти без инициализации (пулы, арены) → отдельная функция с именем, отражающим операцию (например, `pool_alloc`).

### Гарантии

- Пары независимы: наличие одной не влечёт необходимости в другой.
- Имя функции соответствует операции: `create` выделяет хранилище, `init` — нет.
- `destroy` и `deinit` корректно обрабатывают `NULL`.
- `create` включает операции `init`, но неприменима к существующему объекту.

## Типы

- Использовать `stdint.h`, когда точные типы важны и требуется высокая отказоустойчивость.

## Заголовки

- Интерфейс модуля — заголовок, объявляющий его типы и функции.
- Всегда использовать include guard.
- `#pragma once` не используется: ориентир — `-pedantic` C.

## Препроцессор

- `const` / `enum` / `static inline` вместо макросов — когда это нужно; не запрещено.

## Стандарт и сборка

- Явно указывать версию C.
- `-pedantic`, если проект не планирует отклоняться от чистого C.
